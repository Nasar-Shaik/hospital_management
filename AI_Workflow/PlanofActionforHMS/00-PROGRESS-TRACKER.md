## 7. Work-in-Progress Notes / Handoff

**Nothing is half-done.** Working tree clean; all gates green (typecheck 17/17, lint 17/17, build 11/11, boundaries 0 violations across 329 modules, 47 integration tests).

Known gaps, each a deliberate decision rather than an oversight:

- ~~**Audit is not yet atomic with the mutation it describes.**~~ **PAID OFF (2026-07-14, P2.)** `withTransaction` (`core/db/transaction.ts`) is adopted in the patients module; UHID + patient + audit + outbox now commit as one atom. Proven by planting a decoy on the next UHID so the insert failed AFTER the counter was incremented: the counter rolled back, the next registration recovered the same number, and **zero orphan audit rows** were left behind. Every service with a multi-document invariant from here on uses it — a single-document write stays plain, because a transaction around one write is ceremony.
- **The MPI can still be beaten by a race.** Two clerks registering the same person in the same second both search, both see nothing, and both insert. No lock prevents this, because there is no key to lock on — "the same person" is a judgement, not a value. This is precisely why merge is a first-class, permanent operation and not a repair script. The MPI reduces duplicates; only a merge removes one.
- **Branch row-scope is enforced but untested at the matrix level, and there are no branches yet.** `branchScope: "all"` is what every binding carries today (B1–B3 unbuilt), so the `branch` level is currently a no-op in practice. The moment branches ship, a patient with no `branchId` becomes invisible to branch-confined staff — decide then whether unassigned patients are visible to all or to none. **The RBAC matrix suite is the right place to pin this down before it can bite.**
- **No real event consumers.** `apps/workers` acknowledges and logs. That is what closes the loop end to end today; A6 (notifications) registers the first genuine consumer. `patient.patients.merged` has no consumer yet — it does not matter while nothing else stores a `patientId`, and it starts mattering the day appointments ship.
- **`identity.user.rolesChanged` has no fan-out consumer**, so a revoked permission can persist on OTHER pods until the `perm:{userId}` TTL expires (≤ access-token life). Same bound ADR-0009 already accepts for token revocation. The event exists so the fix is a consumer, not a redesign.
- **Anchors are stored in the same database they protect.** That is honest tamper _evidence_, not tamper _proof_ — an attacker with full DB access can rewrite entries and re-seal. Shipping anchors off-box (S3 object-lock / a signed daily digest to the compliance officer) is what makes the chain adversarial, and it is an ops task.
- **`hms_chaintest` is a throwaway tenant** created to prove tamper detection against a live database edit. Harmless; delete it whenever. (`hms_demo`'s trail was reset on 2026-07-14 after the `actorRoles` hashing bug — it now verifies clean from `seq 1`.)
