Total gating integration tests: 46.
  - **Identity is three modules, not one** (`users`, `auth`, `rbac`), because `auth` needs roles for the token and `rbac` needs users for bindings — one module would have been a cycle, which the Constitution forbids. `users` depends on nothing; `auth` and `rbac` both depend on it. Do not "simplify" this back into one module.
- **Phase 1C (RBAC) — DONE (2026-07-13).** `packages/permissions` is now the **authorization catalog**: 144 permissions (taken from Doc 02, never invented), 30 feature flags, 7 editions, 11 default roles with real grants. Three-layer `authorize` (entitlement → permission → row scope) in ADR-0010 order; `perm:{userId}` and `ff:{tenantId}` caches with invalidation in the writing service method. **Permissions fail CLOSED** (Redis outage = cache miss = DB read = same answer) — the exact opposite of the token blocklist, which fails open on purpose; same infrastructure, opposite correct behaviour, so never reason about one from the other.
  - `TENANT_ADMIN` holds 141 of 144: **never** the 3 superadmin codes. That is the only thing stopping a hospital admin from reaching another hospital via a role edit — do not "helpfully" grant them.
  - **Staff directory** (`modules/staff`) — an ORCHESTRATOR that owns no collection. Creating staff touches `users` (identity) + `auth` (credential) + `rbac` (binding); `auth` already depends on `users`, so doing it inside `users` would cycle. It lives one level up: depends on all three, nothing depends on it. `seedTenantAdmin` delegates to it, so user creation has ONE implementation. Same trick will be needed for any use case spanning these modules — do not solve it by weakening a boundary.
- **Web app shell + login — DONE (2026-07-14).** `/login` (password → MFA), `/dashboard`, `/staff`, `/roles`, `/change-password`, `/sessions`; middleware route guard; access token in memory (never localStorage), refresh in the httpOnly cookie (path `/` so middleware can see it), silent refresh ~60s before expiry. `/auth/me` returns permissions for **UI gating only**.
  - **THE HOSTNAME IS THE TENANT, and this shapes the whole frontend.** A browser cannot set `Host`, so it must call the API on the hostname it is browsing. The client therefore takes a PORT, not a base URL. **Dev uses `<slug>.localhost`** (resolves to 127.0.0.1 with no hosts entry) — never the real domain locally: `*.paperlesstech.in` has **wildcard DNS pointing at the production server**, so `demo.paperlesstech.in:3000` in a browser would hit production. CORS is tenant-aware for the same reason (a fixed allowlist cannot work when the origin is per-hospital); dev reflects origins under `TENANT_BASE_DOMAIN`, gated on NODE_ENV.
  - `API_BIND` (owner's pattern from their other project): production binds `127.0.0.1` so only the gateway can reach Express; containers set `0.0.0.0`.
- **Fleet migration CLI (`pnpm --filter @medicore/api migrate -- --all`).** Provisioning converges a NEW tenant; this converges the ones already running. Found the hard way: `hms_demo` was provisioned before Phase 1C, so its admin had **zero permissions** — the code shipped, that database didn't. **Every release that adds a migration or changes the permission catalog must run this.**
- **A2 Subscriptions & editions — DONE (2026-07-14).** `plans` + `usageCounters` in master; the plan catalog is a projection of the code-defined EDITIONS. **Usage is counted live, never stored** — a drifted counter that over-reports would lock a hospital out of hiring. Limits enforced **at creation points only** (HMS-PLAN-001, 402), never mid-workflow: a hospital at its bed limit must still be able to discharge a patient. 80% soft warning, 100% hard block. Downgrades that would strand people are refused. Operator CLI `plan --slug X --plan PLAN_Y` (there is deliberately no self-serve route). SaaS invoicing/dunning deferred — needs a payment gateway.
  - **🔒 SECURITY FIX, do not undo.** `plan:manage` and `featureflag:manage` were originally grouped with the ordinary platform permissions, so **TENANT_ADMIN inherited them and the demo hospital upgraded ITSELF to Enterprise** — any customer could have taken the top edition for free, or switched on a module they never bought. Both are now in the SUPERADMIN group (global scope), which `DEFAULT_ROLES` subtracts from TENANT_ADMIN. **TENANT_ADMIN must hold 139 of 144 — never `plan:manage`, `featureflag:manage`, `superadmin:tenant:manage`, `tenant:impersonate`, `tenant:export`.** `subscription:manage` IS granted (a hospital may see what it bought, not change it). Editions are worth nothing if the customer can edit their own.
  - Lesson: this is precisely what the deferred RBAC matrix suite catches **by construction** rather than by someone happening to try it.
- **A5 Audit & the transactional outbox — DONE (2026-07-14).** The compliance floor. Every mutation of an audited collection is recorded whether the developer remembered or not.
  - **Audit lives in `core`, NOT in a module** (Doc 04 §2.2). A module that could _choose_ to be audited would eventually choose wrong. `core/audit` owns the append path — `auditPlugin` (automatic, per-collection) + `recordAudit` (explicit, for the events that are not document writes: login success/failure, lockout, token reuse, permission denial, role grant/revoke, plan change, audit export). `modules/audit` may only READ. **`auditLogs` has no update or delete path anywhere in the codebase** — every mutating query hook throws. A correction is a NEW entry.
  - **Tamper evidence, honestly scoped.** Each entry carries a gap-free per-tenant `seq` (atomic `$inc` — a deleted entry leaves a hole you cannot explain away) and a SHA-256 leaf hash. A single-writer job seals ranges into hash-chained `auditAnchors` (`audit:chain --seal`), and `--verify` recomputes everything. **Anchoring is periodic, not per-write, on purpose:** a per-write chain needs a lock on the tail, which would make audit the throughput ceiling of the hospital — audit must never be the reason a nurse cannot chart. This detects tampering; it cannot prevent it. Anchors still live in the database they protect (see §5).
  - **Two bugs that only a real round-trip found.** (1) **Mongoose silently defaults an array path to `[]`.** Entries with no `actorRoles` were _hashed_ without the field but _stored_ with an empty array, so the verifier reported TAMPERING on a trail nobody had touched. A tamper alarm that cries wolf is worse than no alarm — the first false positive teaches everyone to ignore it. Fixed with `default: undefined`; write and verify now share ONE projection (`auditLeaf`) so the two field lists can never drift again. (2) A CLI script named `audit` was shadowed by pnpm's built-in `pnpm audit` → renamed `audit:chain`. **Lesson: hash a document you have actually round-tripped through the database, never the object you _intended_ to store.**
  - **The outbox is the ONE event-publishing seam** (ADR-0007, Doc 03 §5.2). `publish()` writes to `outboxEvents` **in the same database, in the caller's transaction when there is one** — a service that saved a patient and then pushed to Redis would be dual-writing to two systems that cannot commit together, and a crash between them silently produces either an un-notified patient or an SMS about a patient who does not exist. The relay lives in `apps/api` (it needs the tenant registry + Connection Manager, which `apps/workers` does not have), is elected by `lock:outbox-relay`, and feeds BullMQ → `apps/workers`. **Delivery is at-least-once BY DESIGN** — `sent` is marked only _after_ enqueueing, so a crash in that window redelivers rather than drops; a lost panic-lab-value notification is a worse incident than a duplicate one. **Every consumer must dedupe on `eventId`.**
  - 5 events live (EVENT_CATALOG "Implemented"). `platform.subscription.changed` is **not** atomic with its own write — the plan lives in the master DB, the outbox in the tenant's — and that gap is documented at the call site rather than hidden.
- **Environment configuration — RESTRUCTURED (2026-07-14).** `apps/api/src/config/profiles.ts` is now the ONE place that knows how local differs from production. Resolution order: **schema default → profile default → environment variable → production invariant**. The last layer is the point: an invariant is not a default and **cannot be overridden** — a production deploy carrying `PASSWORD_MIN_LENGTH=6` gets 12 back plus a `[SECURITY]` error naming the mistake. Secrets are NEVER in profiles.ts (git history is forever); they are environment variables only. The API logs its _effective_ config at boot (`describeConfig()`), because every config bug we hit was invisible — the process looked healthy while quietly aimed at the wrong thing.
  - **Local dev password policy is deliberately weak** (6 chars, no complexity) so `admin@demo.test` / `123456` works. This is safe ONLY because the production invariant makes the weak path unreachable in a hospital. Do not "tidy up" `applyProductionInvariants` — it is the thing that makes the convenience legitimate.
- **A1 Operator Console — DONE (2026-07-14).** The platform can now onboard a hospital without a developer. `pnpm --filter @medicore/api operator` bootstraps the FIRST operator (and refuses to run once any exists — otherwise it is a permanent unauthenticated back door that mints super-admins); every operator after that is created from the console, audited.
  - **Operators live in the MASTER db (`platformUsers`), never in a tenant.** A super-admin acts across hospitals; putting them inside one creates an identity that is simultaneously inside and outside the tenancy boundary — which is precisely how that boundary gets destroyed. Separate population, separate token type (`platform`), separate login host (`admin.<domain>`).
  - **The `platform` token carries NO `tid`.** Two independent barriers: (1) `verifyToken` rejects the wrong token type; (2) even if that were bypassed, `authenticate` compares `claims.tid` to the host-resolved tenant, and `undefined` matches no hospital. A hospital token is rejected at the console for the mirror reason. Verified both directions.
  - **SUPER_ADMIN vs SUPPORT.** Provisioning, suspending and re-pricing are the three actions that take a hospital offline or cost it money — SUPER_ADMIN only. Most operator work is support work, and a support engineer should not be one mis-click from re-pricing a customer.
  - **An operator may NOT read PHI, ever.** No platform route returns patient data and none may be added. Every action that touches a hospital is written into THAT HOSPITAL'S audit trail (`hospital.provisioned`, `hospital.adminIssued`, `hospital.statusChanged`) as well as ours — the customer's compliance officer can see us. That asymmetry is what makes the control plane trustworthy rather than merely powerful.
  - **🔒 Found while building: no RESERVED SLUG list.** A customer could have provisioned the slug `admin` and thereby owned `admin.paperlesstech.in` — the operator console's own hostname. `admin`, `api`, `www`, `app`, `mail`, `console`… are now refused. **The hostname IS the tenant, so a slug is a namespace grab.** Refusing a name is cheap; taking one back from a paying customer is not.
  - Creating a hospital and issuing its first admin is ONE operation. Every previous path allowed "provision now, seed the admin later", which reliably produced a database nobody could enter — a locked room with no key.
- **Authorization is DYNAMIC by construction (hardened 2026-07-14).** The JWT carries who you ARE (`sub`, `tid`, `roles`, `eml`) — **never the 144 permission codes**. Baking permissions into the token is the obvious optimization and it is exactly why so many systems cannot revoke access: a permission in a token is true until the token expires, so a fired employee keeps their access for the token's lifetime while the system _knows_ they are revoked. Instead `authorize` re-derives permissions from the database each request through one shared-Redis read (`perm:{userId}`), and the writing service method drops that key. Cost: one Redis GET. Benefit: "access revoked" means revoked.
  - The browser gets its permission list from `/auth/me` and holds it **in memory** (never `localStorage`, which any XSS can read) — and it is used for **UI gating only**. Tamper with it and the server still returns 403. The client list decides which buttons to _draw_, never what is _allowed_.
  - **`branchIds` (row scope) now comes from the same live bundle, not from the token.** It used to be token-derived, which made ROW scope stale in precisely the case that matters most: a nurse moved off a ward, or restricted during an investigation, kept seeing the old ward's patients until her token expired. Permissions were live and scope was not — and the weaker half silently decided what she could see. They are one bundle now, invalidated together.

Both the audit and event mechanisms it needs now exist and are proven, which is exactly why A5 came first. ② **A6 Notifications** — unblocks forgot/reset-password and gives the outbox its first real consumer. ③ The **super-admin/operator console** (A1's missing HTTP surface). ## 5. Known Technical Debt

_(Format: what · where · why accepted · interest being paid · suggested payoff trigger)_

- **Dev compose uses non-default ports (mongo 27018, redis 6380)** · `infra/docker/docker-compose.yml` + `.env.example` files · another local project already binds 27017/6379 on the dev machine · contributors must not "fix" ports back to defaults · payoff: none needed. **Mongo is 27018 on BOTH sides of the container (`--port 27018`, published `27018:27018`) — do not "normalize" the internal port to 27017.** See §8; that symmetry is a safety property, not tidiness.
- **`pnpm deploy --legacy` flag in api/workers Dockerfiles** · pnpm 10 deploy behavior · simplest working monorepo prod-bundle today · revisit when pnpm stabilizes non-legacy deploy for workspaces.
- **Sprint 0 skipped OpenAPI baseline and RN app scaffolds** · deliberate: OpenAPI is meaningless with zero business routes (P1), Expo apps are P5 · add both at their phases.
- **Access-token revocation fails OPEN when Redis is down** · `middleware/authenticate.ts` + `core/redis/redis.ts` · the blocklist is a cache, and hard-failing every authenticated request during a Redis outage would take the hospital down — a worse outcome than a ≤15-minute revocation delay · interest: a logged-out or compromised token stays usable until it expires (bounded by `ACCESS_TOKEN_TTL_SECONDS`), and ADR-0009 explicitly accepts that bound · payoff trigger: if a customer's threat model demands immediate revocation, shorten the access TTL (a config change) before considering a DB-backed check on the hot path.
- ~~**Auth events are not yet published to the outbox**~~ · **RESOLVED (2026-07-14, A5)** — the outbox and relay exist; auth security events are now in the AUDIT trail (`auth.login.failed`, `auth.token.reuseDetected`, `authz.denied`), which is the right home for them. They are deliberately NOT outbox events: an event with no consumer is speculation. A SIEM feed becomes an outbox consumer when there is a SIEM.
- **Audit is not yet ATOMIC with the mutation it describes** · `core/audit` + every service · Doc 09 §9 wants "audit failures fail the transaction", and today no service opens one — each writes a single collection at a time, so there is no transaction to join · interest: a crash between the mutation and its audit write leaves an unaudited mutation. Bounded: the audit write is _awaited_, so a FAILING write throws and the request fails loudly — it never silently proceeds · **the plumbing is already in place**: `recordAudit`/`publish` both take a `session`, and `auditPlugin` reads `doc.$session()`/`query.getOptions().session`, so adopting transactions requires **zero changes** to the audit layer · payoff trigger: **P2 (Patients)** — the first module with a genuine multi-collection invariant. Adopt `withTransaction` there and audit becomes atomic for free.
- **Audit anchors are stored in the database they protect** · `core/audit/auditChain.ts` · shipping them off-box needs infrastructure (S3 object-lock, a signing key, a delivery channel) that does not exist yet · interest: an attacker with full DB access can rewrite entries AND re-seal the anchors, so today the chain detects careless tampering, not determined tampering · payoff trigger: before the first real customer's data lands — ship the daily anchor root to object-lock storage or email it to the hospital's compliance officer. The chain is already built; only the _destination_ is missing.
- ~~**`identity.user.rolesChanged` has no consumer → stale permissions across pods**~~ · **THIS CLAIM WAS WRONG (corrected 2026-07-14).** I wrote it without checking, and it is not true: `perm:{userId}` lives in **Redis, which every pod shares**, and `invalidateUser` deletes the key there — so an invalidation is platform-wide the instant it happens, not per-pod and not eventually. **Verified live:** an AUDITOR whose role is revoked gets HMS-AUTH-005 on the very next request, with the SAME unexpired token and no re-login. The event remains useful for other consumers (notifications, SIEM); it is not load-bearing for cache correctness. **Lesson: a debt entry asserting a weakness is a claim like any other, and I recorded one I had not tested.**

## 7. Lessons Learned

- (2026-07-12) Writing editions _after_ modules exposed missing modules (dialysis, physio, ED triage…). Lesson: **map packaging → capabilities early**; the sales lens finds architecture gaps that the engineering lens misses.
- (2026-07-12) A mid-review architecture pivot (shared-collections → DB-per-tenant) touched 7 documents. Lesson: keep tenancy assumptions centralized (Doc 03 §1 + ADR) and referenced, not restated, elsewhere — restatements are what go stale.
- (2026-07-12) ADR-0003 (Vite SPA) was correct for its stated scope and superseded within a day when the scope statement changed (public/SEO/white-label surfaces became first-class). Lesson: **an ADR is only as durable as its Context section** — write the scope assumptions explicitly so it's obvious when they break; the supersession process worked exactly as designed.
- (2026-07-12, Phase 1B) The module boundary rule _forced_ a better design. Putting `users`, `credentials` and `roles` in one "auth" module was the obvious move, and it would have created an import cycle (auth needs roles for the token; rbac needs users for bindings). Splitting identity into `users` ← `auth` / `rbac` removed the cycle **and** produced a module where every secret in the platform lives in exactly one folder. Lesson: **when a boundary rule is inconvenient, the design is usually wrong, not the rule.**
- (2026-07-12, Phase 1B) The auth suite passed on its first run — which was itself suspicious. Deliberately breaking the tenant-claim check (`if (false && …)`) proved the isolation test failed as intended; without that step, a vacuous pass and a real pass are indistinguishable. Lesson: **for the assertions that matter most, verify the test fails when the property is removed.** A green suite only means something if you know it can go red.

- (2026-07-14, A2) A route comment asserted "`plan:manage` is granted to no hospital role" — and it was false. TENANT_ADMIN held it, and the demo hospital upgraded itself to Enterprise. The comment survived my own code review because I read it as documentation instead of testing it as a claim. Lesson: **a comment asserting a security property is a hypothesis, not a fact.** Every claim of the form "X cannot do Y" must have a test that tries Y as X.
- (2026-07-14, A5) The audit hash chain reported TAMPERING on a trail nobody had touched — Mongoose silently defaults an array path to `[]`, so entries were hashed one way and stored another. It compiled, it passed typecheck, and it was completely wrong. Lesson: **hash what you have actually round-tripped through the database, never the object you intended to store** — and for a security control, the false-positive path is as dangerous as the false-negative one, because the first false alarm teaches everyone to ignore the alarm.
- (2026-07-14, A5) The same bug also proves the value of testing the _detector_: I only found it because I sealed a real chain and then falsified a real row in MongoDB to watch the alarm fire. Lesson: **a tamper-detection system you have never seen catch a tamper is a decoration.**

- (2026-07-14) **`z.coerce.boolean()` on an environment variable reads `"false"` as `true`.** Env vars are strings and every non-empty string is truthy, so `PASSWORD_REQUIRE_COMPLEXITY=false` silently enabled complexity. Use the `envBool()` helper in `config/env.ts`, which parses the spellings people write and REJECTS anything else. A security flag that reports itself ON while being OFF is the worst possible failure mode.
- (2026-07-14) **`<slug>.localhost` resolves to `::1` (IPv6) BEFORE `127.0.0.1`.** Binding the API to `0.0.0.0` is IPv4-only, so the browser could not reach an API that `curl` reported as perfectly healthy — curl silently falls back to IPv4, a browser does not. In dev, bind dual-stack (leave `API_BIND` empty). Lesson: **when the browser fails but curl succeeds, suspect the address family before you suspect the code.**
- (2026-07-14) **A default is a decision.** `TENANT_BASE_DOMAIN` defaulted to the real production domain, so an unconfigured process was configured _for production_ — and since `*.paperlesstech.in` has wildcard DNS to the live server, our own setup docs pointed a developer's browser at it. Defaults must fail SAFE, and for an environment-shaped setting "safe" means "local". Production names its own domain explicitly.

## 8. Common Mistakes to Avoid (grows with experience)

- Using `suppliers`/`equipment` as collection names (rulings N1/N2 — they're aliases/views of `vendors`/`assets`).
- Putting business logic, DB access, or business API routes inside Next.js (`app/api/*`) — Next.js is presentation-only; Express is the only API (ADR-0012, ruling N9).
- Scaffolding new frontend features with Vite — Vite survives only as Vitest + `packages/ui` playground tooling.
- Putting per-hospital data in the master DB or vice versa — check Doc 03 §2 placement table every time.
- **Granting a commercial permission to a hospital role.** `plan:manage` / `featureflag:manage` decide what a customer PAYS FOR. They belong to the SUPERADMIN group and must never be inherited by TENANT_ADMIN — a customer who can toggle their own flags has a free upgrade. (Happened once; see §1.)
- **Browsing a tenant on the real domain in local dev.** `*.paperlesstech.in` has **wildcard DNS pointing at the production server** — `demo.paperlesstech.in:3000` in a browser goes to production, not your laptop. Use `<slug>.localhost` locally (`TENANT_BASE_DOMAIN=localhost`); it resolves to 127.0.0.1 with no hosts-file entry.
- **Hardcoding an API base URL in the frontend.** `http://localhost:4000` resolves to NO hospital: the browser cannot set `Host`, so the hostname it is browsing is the only thing that selects a tenant database. Configure a PORT (`NEXT_PUBLIC_API_PORT`) and derive the origin from `window.location.hostname`.
- **Shipping a migration without running the fleet job.** A tenant provisioned before the migration keeps running the old schema forever and fails in ways that look like bugs (an admin with zero permissions). Run `pnpm --filter @medicore/api migrate -- --all` after any release that adds a migration or changes the permission catalog.
- **Assuming a loopback address means a local database.** (2026-07-13 near-miss.) An SSH tunnel — `ssh -L 27018:127.0.0.1:27017 user@remote` — bound the _same_ loopback port as our dev Mongo and silently won the bind over Docker. Every connection to `127.0.0.1:27018` then reached a **remote** server, and our integration tests call `dropDatabase()`. Nothing was lost, but only by luck. The harness now refuses to run unless the host is loopback **and** the server has no auth (our dev container runs open; real servers do not), and it will only drop databases named `test_*` / `hms_test-*`. If a suite suddenly refuses to run, check `lsof -nP -iTCP:27018 -sTCP:LISTEN` and `docker ps` — something else has the port.
- **Letting a containerized replica set advertise an address that is only true inside the container.** (2026-07-14, found while writing Compass instructions.) A replica-set client does not talk to the server you named — it asks that server who the members are, **discards your address**, and reconnects to the one it is given. Our mongod listened on 27017 internally, so it advertised `localhost:27017`; on the dev Mac that address is an unrelated **`school_mongodb`** from another project. Docker isolation was never breached — both containers publish a port to the host on purpose, and the _client_ walked from one to the other. And because a replica set is named `rs0` by default on both sides, the driver could not tell it had crossed projects: it believed it had simply found its primary. The only thing that stopped a cross-project connection was luck — the other server advertised a Docker-internal hostname that did not resolve (`getaddrinfo ENOTFOUND mongodb`). **Fix: mongod now listens on 27018 _inside_ the container too, published `27018:27018`, advertising `localhost:27018` — one address that is true on both sides.** Discovery is self-consistent, so a client that forgets `directConnection=true` still lands on the right server. Keep the flag regardless: from inside another container, `localhost` means that container. Same class of bug as Kafka's `advertised.listeners`. **Never "normalize" the internal port back to 27017.**
- **Assuming a `services:` container in GitHub Actions can be a replica set.** It cannot — Actions gives no way to pass a command, so `mongo:7` there is a **standalone**, and a standalone supports no transactions at all. Ours was standalone while the comment above it claimed otherwise, which would have failed at the first `withTransaction` in P2 with an error pointing nowhere near the cause. CI now starts Mongo with an explicit `docker run --replSet`, waits for the primary, and **proves a transaction commits before any suite runs** — so the infrastructure fails loudly at its own step rather than inside an unrelated assertion.
- **Stamping fields in Mongoose `pre("save")`.** Schema validation runs _before_ save hooks, so a `required` field stamped there fails validation. Stamp in `pre("validate")` (this is why `tenantScopePlugin` does).
- **Writing an integration test that touches Mongo but not Redis.** The tenant registry is a **read-through cache**: dropping the master DB while `tenant:{slug}` is still cached leaves the app resolving a tenant that no longer exists (symptom: "Slug already taken" on a freshly dropped database). Test setup must drop **both** — `dropDatabases()` **and** `flushTestCache()`. The application never produces that split-brain state on its own; only a test harness can.
- **Asserting on a fail-soft dependency without running it.** Cache helpers fail soft by design, so an auth test that checks "the logged-out token is blocklisted" **passes vacuously with no Redis running** — "revoked" and "never revoked" look identical. This is why the auth suite asserts Redis is reachable and CI runs a real `redis` service. Any future assertion that rests on a fail-soft path needs the same treatment.
- **Importing an ambient `const enum` from a library under `isolatedModules`** (e.g. `Algorithm.Argon2id` from `@node-rs/argon2`) — it typechecks in an editor and fails the build. Pin the value and assert the result instead (`core/crypto/password.ts`).
- **Forgetting `asyncHandler` on an async Express route.** Express 4 does not forward rejections from async handlers: the error never reaches the error middleware and the client hangs until timeout. Every async route wraps in `asyncHandler` (`core/http/asyncHandler.ts`).
- Aggregating dashboards from OLTP collections "temporarily."
- Confusing the hospital's own helpdesk (`helpdeskTickets`, tenant DB) with SaaS support (`supportTickets`, master DB).
- Treating `00-PROGRESS-TRACKER.md`/this file as optional paperwork — they are the only memory the next agent has.
