Total gating integration tests: 46.
  - **Identity is three modules, not one** (`users`, `auth`, `rbac`), because `auth` needs roles for the token and `rbac` needs users for bindings — one module would have been a cycle, which the Constitution forbids. `users` depends on nothing; `auth` and `rbac` both depend on it. Do not "simplify" this back into one module.
- **Phase 1C (RBAC) — DONE (2026-07-13).** `packages/permissions` is now the **authorization catalog**: 144 permissions (taken from Doc 02, never invented), 30 feature flags, 7 editions, 11 default roles with real grants. Three-layer `authorize` (entitlement → permission → row scope) in ADR-0010 order; `perm:{userId}` and `ff:{tenantId}` caches with invalidation in the writing service method. **Permissions fail CLOSED** (Redis outage = cache miss = DB read = same answer) — the exact opposite of the token blocklist, which fails open on purpose; same infrastructure, opposite correct behaviour, so never reason about one from the other.
  - `TENANT_ADMIN` holds 141 of 144: **never** the 3 superadmin codes. That is the only thing stopping a hospital admin from reaching another hospital via a role edit — do not "helpfully" grant them.
  - **Staff directory** (`modules/staff`) — an ORCHESTRATOR that owns no collection. Creating staff touches `users` (identity) + `auth` (credential) + `rbac` (binding); `auth` already depends on `users`, so doing it inside `users` would cycle. It lives one level up: depends on all three, nothing depends on it. `seedTenantAdmin` delegates to it, so user creation has ONE implementation. Same trick will be needed for any use case spanning these modules — do not solve it by weakening a boundary.
- **Web app shell + login — DONE (2026-07-14).** `/login` (password → MFA), `/dashboard`, `/staff`, `/roles`, `/change-password`, `/sessions`; middleware route guard; access token in memory (never localStorage), refresh in the httpOnly cookie (path `/` so middleware can see it), silent refresh ~60s before expiry. `/auth/me` returns permissions for **UI gating only**.
  - **THE HOSTNAME IS THE TENANT, and this shapes the whole frontend.** A browser cannot set `Host`, so it must call the API on the hostname it is browsing. The client therefore takes a PORT, not a base URL. **Dev uses `<slug>.localhost`** (resolves to 127.0.0.1 with no hosts entry) — never the real domain locally: `*.paperlesstech.in` has **wildcard DNS pointing at the production server**, so `demo.paperlesstech.in:3000` in a browser would hit production. CORS is tenant-aware for the same reason (a fixed allowlist cannot work when the origin is per-hospital); dev reflects origins under `TENANT_BASE_DOMAIN`, gated on NODE_ENV.

Found the hard way: `hms_demo` was provisioned before Phase 1C, so its admin had **zero permissions** — the code shipped, that database didn't. **Every release that adds a migration or changes the permission catalog must run this.**
- **A2 Subscriptions & editions — DONE (2026-07-14).** `plans` + `usageCounters` in master; the plan catalog is a projection of the code-defined EDITIONS. **Usage is counted live, never stored** — a drifted counter that over-reports would lock a hospital out of hiring. Limits enforced **at creation points only** (HMS-PLAN-001, 402), never mid-workflow: a hospital at its bed limit must still be able to discharge a patient. 80% soft warning, 100% hard block. Downgrades that would strand people are refused. Operator CLI `plan --slug X --plan PLAN_Y` (there is deliberately no self-serve route). SaaS invoicing/dunning deferred — needs a payment gateway.

Both are now in the SUPERADMIN group (global scope), which `DEFAULT_ROLES` subtracts from TENANT_ADMIN. **TENANT_ADMIN must hold 139 of 144 — never `plan:manage`, `featureflag:manage`, `superadmin:tenant:manage`, `tenant:impersonate`, `tenant:export`.** `subscription:manage` IS granted (a hospital may see what it bought, not change it). Editions are worth nothing if the customer can edit their own.

- **A5 Audit & the transactional outbox — DONE (2026-07-14).** The compliance floor. Every mutation of an audited collection is recorded whether the developer remembered or not.
  - **Audit lives in `core`, NOT in a module** (Doc 04 §2.2). A module that could _choose_ to be audited would eventually choose wrong. `core/audit` owns the append path — `auditPlugin` (automatic, per-collection) + `recordAudit` (explicit, for the events that are not document writes: login success/failure, lockout, token reuse, permission denial, role grant/revoke, plan change, audit export). `modules/audit` may only READ. **`auditLogs` has no update or delete path anywhere in the codebase** — every mutating query hook throws. A correction is a NEW entry.
  - **Tamper evidence, honestly scoped.** Each entry carries a gap-free per-tenant `seq` (atomic `$inc` — a deleted entry leaves a hole you cannot explain away) and a SHA-256 leaf hash. A single-writer job seals ranges into hash-chained `auditAnchors` (`audit:chain --seal`), and `--verify` recomputes everything. **Anchoring is periodic, not per-write, on purpose:** a per-write chain needs a lock on the tail, which would make audit the throughput ceiling of the hospital — audit must never be the reason a nurse cannot chart. This detects tampering; it cannot prevent it. Anchors still live in the database they protect (see §5).
  - **Two bugs that only a real round-trip found.** (1) **Mongoose silently defaults an array path to `[]`.** Entries with no `actorRoles` were _hashed_ without the field but _stored_ with an empty array, so the verifier reported TAMPERING on a trail nobody had touched. A tamper alarm that cries wolf is worse than no alarm — the first false positive teaches everyone to ignore it. Fixed with `default: undefined`; write and verify now share ONE projection (`auditLeaf`) so the two field lists can never drift again. (2) A CLI script named `audit` was shadowed by pnpm's built-in `pnpm audit` → renamed `audit:chain`. **Lesson: hash a document you have actually round-tripped through the database, never the object you _intended_ to store.**
  - **The outbox is the ONE event-publishing seam** (ADR-0007, Doc 03 §5.2). `publish()` writes to `outboxEvents` **in the same database, in the caller's transaction when there is one** — a service that saved a patient and then pushed to Redis would be dual-writing to two systems that cannot commit together, and a crash between them silently produces either an un-notified patient or an SMS about a patient who does not exist. The relay lives in `apps/api` (it needs the tenant registry + Connection Manager, which `apps/workers` does not have), is elected by `lock:outbox-relay`, and feeds BullMQ → `apps/workers`. **Delivery is at-least-once BY DESIGN** — `sent` is marked only _after_ enqueueing, so a crash in that window redelivers rather than drops; a lost panic-lab-value notification is a worse incident than a duplicate one. **Every consumer must dedupe on `eventId`.**
  - 5 events live (EVENT_CATALOG "Implemented"). `platform.subscription.changed` is **not** atomic with its own write — the plan lives in the master DB, the outbox in the tenant's — and that gap is documented at the call site rather than hidden.
- **Environment configuration — RESTRUCTURED (2026-07-14).** `apps/api/src/config/profiles.ts` is now the ONE place that knows how local differs from production. Resolution order: **schema default → profile default → environment variable → production invariant**. The last layer is the point: an invariant is not a default and **cannot be overridden** — a production deploy carrying `PASSWORD_MIN_LENGTH=6` gets 12 back plus a `[SECURITY]` error naming the mistake. Secrets are NEVER in profiles.ts (git history is forever); they are environment variables only. The API logs its _effective_ config at boot (`describeConfig()`), because every config bug we hit was invisible — the process looked healthy while quietly aimed at the wrong thing.
  - **Local dev password policy is deliberately weak** (6 chars, no complexity) so `admin@demo.test` / `123456` works. This is safe ONLY because the production invariant makes the weak path unreachable in a hospital. Do not "tidy up" `applyProductionInvariants` — it is the thing that makes the convenience legitimate.
- **A1 Operator Console — DONE (2026-07-14).** The platform can now onboard a hospital without a developer. `pnpm --filter @medicore/api operator` bootstraps the FIRST operator (and refuses to run once any exists — otherwise it is a permanent unauthenticated back door that mints super-admins); every operator after that is created from the console, audited.
  - **Operators live in the MASTER db (`platformUsers`), never in a tenant.** A super-admin acts across hospitals; putting them inside one creates an identity that is simultaneously inside and outside the tenancy boundary — which is precisely how that boundary gets destroyed. Separate population, separate token type (`platform`), separate login host (`admin.<domain>`).
  - **The `platform` token carries NO `tid`.** Two independent barriers: (1) `verifyToken` rejects the wrong token type; (2) even if that were bypassed, `authenticate` compares `claims.tid` to the host-resolved tenant, and `undefined` matches no hospital. A hospital token is rejected at the console for the mirror reason. Verified both directions.
  - **SUPER_ADMIN vs SUPPORT.** Provisioning, suspending and re-pricing are the three actions that take a hospital offline or cost it money — SUPER_ADMIN only. Most operator work is support work, and a support engineer should not be one mis-click from re-pricing a customer.
  - **An operator may NOT read PHI, ever.** No platform route returns patient data and none may be added. Every action that touches a hospital is written into THAT HOSPITAL'S audit trail (`hospital.provisioned`, `hospital.adminIssued`, `hospital.statusChanged`) as well as ours — the customer's compliance officer can see us. That asymmetry is what makes the control plane trustworthy rather than merely powerful.
  - **🔒 Found while building: no RESERVED SLUG list.** A customer could have provisioned the slug `admin` and thereby owned `admin.paperlesstech.in` — the operator console's own hostname. `admin`, `api`, `www`, `app`, `mail`, `console`… are now refused. **The hostname IS the tenant, so a slug is a namespace grab.** Refusing a name is cheap; taking one back from a paying customer is not.
  - Creating a hospital and issuing its first admin is ONE operation. Every previous path allowed "provision now, seed the admin later", which reliably produced a database nobody could enter — a locked room with no key.
- **Authorization is DYNAMIC by construction (hardened 2026-07-14).** The JWT carries who you ARE (`sub`, `tid`, `roles`, `eml`) — **never the 144 permission codes**. Baking permissions into the token is the obvious optimization and it is exactly why so many systems cannot revoke access: a permission in a token is true until the token expires, so a fired employee keeps their access for the token's lifetime while the system _knows_ they are revoked. Instead `authorize` re-derives permissions from the database each request through one shared-Redis read (`perm:{userId}`), and the writing service method drops that key. Cost: one Redis GET. Benefit: "access revoked" means revoked.
  - The browser gets its permission list from `/auth/me` and holds it **in memory** (never `localStorage`, which any XSS can read) — and it is used for **UI gating only**. Tamper with it and the server still returns 403. The client list decides which buttons to _draw_, never what is _allowed_.
  - **`branchIds` (row scope) now comes from the same live bundle, not from the token.** It used to be token-derived, which made ROW scope stale in precisely the case that matters most: a nurse moved off a ward, or restricted during an investigation, kept seeing the old ward's patients until her token expired. Permissions were live and scope was not — and the weaker half silently decided what she could see. They are one bundle now, invalidated together.
- **P2 — Patient master & MPI — DONE (2026-07-14).** The first PHI collection, and the first module where the platform stops being infrastructure and starts being a hospital.
  - **The UHID is the patient's number for life**, tenant-scoped, allocated from the `counters` sequence (atomic `$inc`, never read-then-write) **inside the registration transaction**. That serializes registration per hospital — two clerks registering at the same instant contend on the counter and one is retried. That is the trade we want: allocating outside the transaction never blocks but burns a number on every abandoned registration, and "why does our register jump from 4417 to 4419" is a question nobody should have to answer. At a few registrations a minute the contention is invisible.
  - **The MPI refuses; it never guesses.** A probable duplicate (score ≥ 60) fails with `HMS-PAT-002` carrying the candidates AND why each matched, and a human decides. Overriding needs `patient:merge` and is separately audited (`patient.duplicateOverridden`). **The asymmetry sets every number:** a missed duplicate costs a second chart (ugly, fixable); a wrong merge puts one person's allergies on another person's record (a clinical safety incident, near-unfixable). So detection is aggressive and merging is conservative — never the reverse. No phonetic matching: Soundex/Metaphone are tuned for English, mangle Indian names, and their failure mode is the false MERGE.
  - **Nothing is ever deleted.** A merge marks-and-links: the merged row keeps its UHID (already on a wristband, a lab slip, an insurance claim) and gains a `mergedInto` pointer. Chains are refused — merging into an already-merged record would force every consumer re-pointing a `patientId` to walk a linked list that will eventually contain a cycle.
  - **Patients are NOT feature-flagged and NOT plan-limited.** Every edition registers patients; `maxPatients` stays unset in every edition on purpose. Seats and beds are things a hospital buys — patients are people who walk in.
- **`withTransaction` is live (`core/db/transaction.ts`) and the A5 audit debt is PAID.** UHID + patient + audit + outbox commit as one atom. `recordAudit`/`publish`/`auditPlugin` have accepted a session since A5, so adopting it changed none of that machinery. **The callback may run more than once** (write-conflict retry) — so it must contain database work only; anything else belongs in the outbox. Proven, not assumed: planting a decoy on the next UHID made the insert fail _after_ the counter moved, and the counter rolled back, the next registration recovered the same number, and zero orphan audit rows remained.
- **RBAC matrix suite — SHIPPED (2026-07-14).** Deferred since 2026-07-13; built once PHI existed, because from that moment an authorization bug is a **breach**, not a bug. 128 release-gating tests; total gating integration tests **47 → 175**.
  - **The coverage test is the one that matters.** Any suite can assert that a route you thought about is protected; the hard problem is the route nobody thought about. So it holds NO hand-written route list — it reads the **shipped Express app** and fails if any `/api/v1` route lacks a permission, or carries one nobody wrote an expectation for. **A new unprotected route breaks the build.**
  - **This required making the middleware self-describing.** `authorize()` / `authenticate()` / `authenticatePlatform()` / `requirePlatformRole()` tag themselves (`core/http/routeInventory.ts`), and the tags are read back off Express's router stack. `pnpm --filter @medicore/api routes` prints the real authorization surface. **The first honest run mislabelled 14 operator routes as PUBLIC** because the platform middleware was untagged — an audit tool that lies about 14 routes is worse than no audit tool, so operator auth is tagged DISTINCTLY from tenant auth (they are mutually-rejecting populations; conflating them would hide a route mounted on the wrong side of the tenancy boundary).
  - **Expectations are DERIVED from `DEFAULT_ROLES`, never typed out.** A hand-maintained expectation table is a second source of truth that drifts toward the code until it asserts nothing. Two vacuity guards, because a green suite that tests nothing is worse than no suite: `routeInventory` must find > 20 routes (an Express upgrade that broke it would return `[]` and every test would pass), and `permissionsOf()` **throws** if a role resolves to zero permissions (an empty set means "expect 403 everywhere", which every denied route satisfies).
  - **Proven by FALSIFICATION, not by going green.** Deleting `authorize()` from one patients route → the suite named that route. Reintroducing the P2 branch-scope bug → it reproduced the exact symptom (`expected 0 to be greater than 0`; the admin seeing zero patients). **Never trust a new test suite that has only ever passed.**
- **E1 Appointments + D2 doctor schedules — DONE (2026-07-14).** The clinical loop closes: register a patient, book them with a doctor.
  - **"A doctor cannot be in two places at once" is a UNIQUE PARTIAL INDEX (`one_doctor_one_slot`), not a service check** — and that distinction is the module. Two receptionists both read "10:30 is free" and both write; the window between read and write cannot be closed in application code, only arbitrated by the database. The service therefore does NOT check availability before booking: it writes, catches the duplicate-key error, and turns it into `HMS-APT-001` **carrying the next open slots**, so the loser rebooks in one motion instead of starting the flow over with a patient standing there. Same shape as the UHID counter: when correctness needs an atomic decision, make the DATABASE make it.
  - **`occupies` is derived state and exists only for that index.** Mongo's `partialFilterExpression` cannot say `status: {$in: [...]}`, so the occupying statuses collapse into one boolean, maintained in the SAME write as `status` (`repo.setStatus`). If it ever drifts, a cancelled appointment holds its slot forever and nobody can explain why 10:30 is unbookable.
  - **Slots are COMPUTED, never stored.** A stored slot table is millions of rows describing what one row already says, and it drifts the instant a doctor's hours change — leaving bookable slots that no longer exist. Only appointments are durable. (`slots.ts` also records the DST assumption: minutes-from-local-midnight is correct until a hospital in a DST zone is onboarded, at which point the fix is a per-tenant IANA timezone, not arithmetic patched in place.)
  - **Rescheduling creates a new appointment and LINKS the old one; it does not overwrite `startAt`.** "Booked Tuesday, moved to Friday" is evidence somebody will need — for a complaint, a no-show dispute, a clinical timeline. The new slot is booked BEFORE the old one is released, so a failed reschedule leaves the patient holding their original appointment rather than nothing.
  - Token numbers are assigned at **check-in**, in arrival order — not at booking. Who is seen next is decided by who is here.
- **ADR-0010 LAYER 1 (entitlement) is finally exercised.** Appointments is the first feature-gated module (`OPS_APPOINTMENTS`); until it shipped, no route carried a flag and layer 1 had never run end to end. An unsubscribed hospital now gets `HMS-PLAN-002` ("not in your edition"), never `HMS-AUTH-005` — **that ordering is the point**: the first sends the admin to sales, the second sends them hunting through the role editor for a permission that can never help them. Note every edition includes `OPS_APPOINTMENTS`, so the unentitled case is a tenant with NO plan (provisioned, not yet subscribed) — which is exactly the case that must not get the product for free.
- **✅ CLOSED (2026-08-11) — OpenAPI debt.** Was: "69 routes and `packages/api-client` is hand-maintained — precisely how a client silently drifts from the API it claims to speak." It had drifted, exactly as predicted: 15 `branchId` mismatches, including one that made a shipped Multi-Branch feature unreachable from the web app. Now: `validate()` tags its Zod schema onto the route and the spec reads it back off the router stack (125 request bodies, 42 query, 127 path params), generation is deterministic, and three gates run in `pnpm gate` — drift, additive-only compatibility, and client coverage/branch parity. **The remaining half — response DTOs — closed the same day (Phase 2):** 260 of 265 operations now publish a real success schema across 165 named components, each tied to the DTO its service returns by a type-level proof, and `ok()` verifies the payload against it outside production so the 1,409 integration tests double as contract tests. That comparison found three live defects nobody had seen: prescription lines serialized as Mongoose internals on the create path (leaking `$__parent` with the whole raw document, `tenantId` included), every dispense shipping `creditOverride: {}`, and `getRole` typed so the role editor could not read the permissions it edits — plus 37 client/server response divergences. The client is still hand-written and now field-by-field verified; generating it is a decision on its own merits rather than a rescue. See PROJECT-STATUS.md.
- **Appointments UI — DONE (2026-07-14).** `/appointments`: pick a doctor and a day, click an open slot. **No free-text time field** — the clerk can only book slots that exist, so the commonest bad booking is impossible to EXPRESS rather than merely rejected. Action buttons are derived from the state machine, so the UI cannot offer an edge the server would refuse. **The lost-race path is a feature:** when another desk wins the slot, the grid refreshes and names the slot that went, so the clerk rebooks in one motion — the difference between a front desk that works and one that gets worked around on paper. Clinic hours are edited on the same screen (the person who finds there are no slots is the person who must fix it), and `HMS-PLAN-002` surfaces as a plan message, never a permissions error.
- **Orders — DONE (2026-07-14).** The spine that carries work between departments (ADR-0013 §3, STATE_MACHINE_CATALOG §15). **ONE polymorphic object** — lab, radiology, pharmacy, procedure, referral, admission, diet — placed against an **Encounter, never a note**: documentation is not the thing that requests work, an order must survive a note being amended, and a diagnostic centre has orders with no consultation at all.
  - **"Orders appear automatically in the destination department" is a QUERY, not a hand-off.** The lab's worklist is `?category=lab&outstanding=true`, so an order joins it the instant it commits. There is no "send to lab" step and therefore no step to forget. `order.placed` is published in the order's own transaction.
  - **`completed → verified` is a second pair of eyes, and it is load-bearing.** The technician who ran the test cannot certify it; a DOCTOR cannot verify their own order. Collapsing the two lets an unverified result reach the person who will act on it.
  - **The polymorphism has ONE sharp edge and it is closed:** a generic `order:verify` would let a PATHOLOGIST sign off a CT scan. Verifying a `lab` order also requires `lab:approve`; `radiology` requires `radiology:sign` — permissions that ALREADY EXISTED, so this cost a lookup table (`order.authority.ts`) and no new RBAC concepts. **That file is the whole surface; each new destination module adds a row.**
  - **A critical result alerts SYNCHRONOUSLY**, inside the request that recorded it — before verification, long before release. The outbox is durable, but _durable_ and _fast_ are different promises, and a relay a minute behind is fine for a welcome mail and unconscionable for a potassium of 7.2. `CRITICAL_RESULT_FLAGGED` is the **audit trail, not the alert**.
  - **The patient leaves `awaiting_results` only when NOTHING is outstanding.** A doctor who orders three tests sends the patient away once and expects them back once; moving the encounter on the first result would call them in to a doctor still holding two blanks. The question is a COUNT ("is anything still owed"), never a flag — a flag would have to be maintained by every path that places or cancels an order, and one of them would forget.
  - **`priorityRank` is derived, never the word.** Sorting the priorities alphabetically gives emergency, routine, stat, urgent — `routine` above `stat`. A list that looks sorted, is sorted, and is lethal.
  - **`requestId` is optional idempotency.** A double-click must not draw two tubes of blood; a repeat blood sugar two hours later is medicine, not a mistake — so the key is supplied by the client, never derived from the content.
  - **The web's two "idempotency keys" were clocks (found 2026-08-12).** `` `ord-${encounterId}-${code}-${Date.now()}` `` and `` `dsp-${id}-${Date.now()}` `` — a new key on every click, so the double-click each was written to prevent went straight through. A key derived from the clock protects nothing and **looks exactly like a key that does**; both had a careful comment above them explaining the protection they were not providing. The rule that survives: a key is minted when the user COMMITS, held across retries of that intent, and dropped when the request changes.
  - **Superseded as the general mechanism (2026-08-11), not replaced.** `Idempotency-Key` is now a header honoured on 24 operations, sitting in FRONT of these per-module guards; the body `requestId` still works and still answers exactly as it did. Two mechanisms was the point: the header is generic and covers the wallet, which had nothing at all, while rewriting orders' `duplicate: true` reply would have been a breaking change for no gain. See `docs/IDEMPOTENCY.md`.
- **Billing core — DONE (2026-07-16, demo slice 1).** The charge ledger. **Money is an integer number of PAISE, everywhere** — `0.1 + 0.2 !== 0.3`, and a hospital that cannot reconcile its day's takings to the rupee stops trusting the software, rightly.
  - **ONE CODE PATH BILLS BOTH HOSPITAL TYPES, and this is proven live:** Sunrise (private) is charged ₹500 + ₹350 + ₹450 = **₹1300**; District General (government) is charged **₹0** for the identical care, through the same endpoints, with the same line items. The only difference is `policy.billingMode` from the org preset. **No code reads `organizationType`** — `organizations.test.ts` greps the source and fails if anyone ever writes the branch.
  - **`zero_tariff` is a TARIFF, not an off-switch.** A charge carries BOTH `listPrice` (what the care is worth) and `amount` (what the patient owes). Government → `amount: 0`, `listPrice` intact. Free to the PATIENT is not free to the STATE, which still has to cost the encounter and report drug consumption. **Skipping the charge would have destroyed exactly the numbers a government hospital exists to report.**
  - **A ₹0 bill finalizes straight to `paid`.** Otherwise a govt hospital accumulates "unpaid" invoices nobody will ever pay, every outstanding-balance report becomes meaningless, and the product gets blamed for a problem it invented.
  - **BILLING LISTENS; NOTHING CLINICAL DEPENDS ON IT.** `encounter.started` → consultation fee, `order.placed` → cost of the test, `order.cancelled` → reversal, all via the outbox. If `startEncounter` called `postCharge`, billing would be upstream of every clinical module, a bad tariff could fail a registration, and the graph would cycle the moment billing read an encounter (it does). **The arrow points inward. Do not invert it.**
  - **The double-billing invariant is an INDEX** (`one_charge_per_cause`, unique on `sourceId`+`code`), not an `if`. At-least-once delivery is the DESIGN — the consumer WILL run twice. Falsified: without it, one consultation bills 3× and one blood test 2×.
  - **A missing tariff entry NEVER blocks a clinical action.** The order still reaches the lab; the charge posts ₹0 with a loud log. A biller's data-entry backlog must not be able to stop a doctor investigating a patient.
  - **Finalizing FREEZES the lines** and assigns the number from an atomic counter. An invoice that can be edited once it is in a patient's hand is not a document, it is a suggestion; a duplicate invoice number is a tax problem, not a display bug.

The order is placed by the consumer and not inline because `placeOrder` opens its own transaction and `withTransaction` is NOT re-entrant: calling it inside the signing transaction would commit the order separately from the signature, and a crash between them leaves pharmacy work for a prescription nobody signed.

- **Admission + transfer — DONE (2026-07-16, `<ADM-1>`).** `admitPatient` closes the OP encounter (`admitted`, terminal) and opens an **IP encounter in the same Episode of Care**, both in ONE transaction — `one_open_encounter_per_patient` is a unique partial index on `open`, so the OP half must stop being open before the IP half starts. **The IP encounter IS the admission**: there is no `admissions` collection, because a second object meaning "this patient is here" is the exact shape ADR-0013 was written to kill. `modules/admissions` owns `wardNotes` ONLY (progress notes + one discharge summary) and orchestrates the discharge; `encounters` owns admitting, discharging and the bed. New `/ward` screen.

Admitted 22:00, discharged 09:00 = TWO days — the bed was unsellable on both, and 24-hour blocks would bill that stay ₹0, which is a hole the ward papers over by admitting at one minute past midnight. **Each night is its own charge** (`<encounterId>:night:<n>`); keyed on the encounter, `one_charge_per_cause` posts night 1 and silently swallows the rest of a five-day stay.
  - **A transfer is a HANDOVER, not `PATCH { doctorId }`.** It requires a reason, appends it to `history` with the actor, and emits an event. A silent move has no answer to "who was responsible for this patient at 4pm", which is asked exactly once, in the worst circumstances.

Signing a prescription re-screens server-side: an allergy CONTRAINDICATION refuses the signature (HMS-RX-001) unless an override reason is supplied, which is snapshotted onto the prescription as `safetyOverride`. Cross-sensitivity / interaction / duplicate-therapy WARN but never block. UI: an allergies panel + a block/override flow on `/my-patients`, an allergy banner on `/pharmacy`. Proven live in a browser at sunrise. 711 tests (674 int + 37 unit). **The design decision that matters: the severity LADDER.** Only a contraindication blocks; everything else informs. A system that hard-blocks every warning trains the prescriber to click past all of them, and the day the real one fires it is just another box to dismiss. See the resolved debt in §5 for what is still missing (it is a net, not a formulary).
  - **A rejected auth cookie taught the general rule, and allergy reads apply it:** an allergy is a fact about the PERSON, so its read is keyed on `patientId` and NEVER on the branch (`allergy.repository.ts` deliberately does not call `scopeFilter`). A branch filter would hide an allergy recorded at another branch, and the check would wave the fatal drug through against an empty list. The permission scope says `tenant` out loud rather than leaving a `branch` label the repo quietly disobeys — the lesson from the `prescription:create` scope bug, applied forward.

## 1b. The Encounter model (ADR-0013 / ADR-0014, 2026-07-14) — read this before touching anything clinical

- **The Encounter is the central clinical object, NOT the Appointment.** An appointment is a _promise of a future encounter_; the encounter begins on arrival. Origins: `appointment | walk_in | emergency | referral | camp | telemedicine | corporate | transfer`. A government hospital or a clinic creates encounters **directly** — no fabricated appointment, ever.
- **`visit` is a RETIRED word.** The glossary used to define `Visit` and _forbid_ `encounter`; that is reversed. We use the FHIR R4 names (`Encounter`, `EpisodeOfCare`, `ServiceRequest`→Order, `DiagnosticReport`→Result) because **ABDM/NHCX — which we are already committed to — is FHIR R4.** The name makes integration a mapping instead of a translation, and costs nothing today.
- **Order is the spine.** "Doctor orders appear automatically in the destination department" is not a queue feature — it is `order.order.placed` → a work item. Orders are ONE polymorphic object with a `category`, placed against an **Encounter, never a note** (documentation is not the thing that requests work; a diagnostic centre has orders and no consultation).
- **`awaiting_results` is the state that matters most.** A patient who goes to the lab and comes back keeps the SAME encounter. Without it, hospitals re-register them and fragment one visit into two — the commonest data-quality disaster in an OPD (it double-counts the census and splits the bill).
- **Admission opens a LINKED inpatient encounter in the same Episode of Care.** It does NOT extend the OP encounter. Continuity is a read concern (a timeline over the episode); separation is a billing and statutory concern (OP/IP tariffs differ; census/ALOS/NABH count encounters). **Two encounters can always be joined; one can never be split back apart.**
- **The work queue is a PROJECTION, never a source of truth.** `workItems` is a read model built by outbox consumers, idempotent on `(sourceType, sourceId)`, rebuildable from the domain. An authoritative queue table = a dual write to two systems that cannot commit together — the exact failure the outbox exists to prevent, sited where a dropped write means a blood test nobody performs. The engine has zero clinical vocabulary → it is a **platform module** School ERP inherits.
- **NO configurable workflow engine.** The three canonical journeys are ONE state graph plus five policy switches (`entry`, `tokenIssuedAt`, `routing`, `billingMode`, `pharmacy`) in `encounterPolicy`. A BPMN engine is "different codebases" hidden inside data, where CI cannot see it and no test can cover it.
- **`organizationType` is a PRESET, never a branch — `if (organizationType === "government")` is FORBIDDEN.** It selects flags/tariff/policy at provisioning and is descriptive thereafter. Constitution §1 demands 25 org types from one codebase; a type branch is a 26th axis CI cannot enforce.
- **"Government hospital" does NOT mean "skip billing" — it means a ZERO-RATED TARIFF.** Every charge still posts to the encounter at ₹0, because a govt hospital is legally required to report drug consumption, per-patient cost and NHM utilisation, and that data cannot be reconstructed. A zero-rupee invoice is a record; a missing invoice is a hole. (Also: govt hospitals run _paid private wards_ — a hard branch would make them unsellable.)
- **Feature flags unbundled:** `module.ops.opd` is independent of `module.ops.appointments`, so OPD can be bought without the appointment book. Today it cannot — that is the bug ADR-0013 closes.

## 3. Architectural Assumptions (validate before relying on)

- Tenant count ~50–500 in first years; master registry fits in Redis cache comfortably.
- Largest single hospital ≈ 1,000 beds → one replica set per tenant DB suffices for years; within-DB sharding is a documented escape hatch, not a plan.
- Connection Manager LRU cap ~200 open tenant connections per API pod is safe (validate under load in P9).
- India-first go-to-market (GST, ABDM, NHCX, NABH weighting); architecture must not hardcode India (tax/ID/compliance are per-tenant config).
- AI features are advisory-only in all jurisdictions we enter; no autonomous clinical action is on any roadmap.

Proven live: penicillin allergy → amoxicillin blocked → override signs and records. **STILL open (the debt narrows, not closes):** renal/hepatic dosing, paediatric weight bands, pregnancy category, dose ceilings — `drugSafety` is a net over the 15 demo drugs, NOT a formulary. - **The pharmacist's "this visit owes" figure is eventually consistent** · `apps/web/app/pharmacy/page.tsx` · billing LISTENS, so the drug charge is posted by a consumer after the relay delivers `medication.dispensed` — it does not exist when `dispense` returns · interest: read once and the counter shows the pre-dispense total (₹500.00 for a visit that owes ₹589.00) — the pharmacist reads out the wrong number with the drugs in their hand. Mitigated by re-reading 1.5s later, which is a timer, not a guarantee · payoff trigger: when the pharmacy takes payment on this screen. ## 5b. Tenancy rules borrowed from the School ERP (2026-07-14) — write these into the module that needs them

The owner's School ERP runs the same architecture (host-as-selector, master registry, DB-per-tenant, Redis host cache, connection manager). Comparing them surfaced five things worth keeping:

- ✅ **Negative caching — DONE.** A miss is now cached (`TENANT_MISS_CACHE_TTL_SECONDS`, 30s). Without it, every request to an unknown host was an uncached query against the MASTER registry — the one DB that routes every hospital — and we publish wildcard DNS, so a stranger spraying `a1.paperlesstech.in`, `a2.…` was a free denial of service against routing for ALL customers. **Remembering an absence obliges you to forget it the instant it stops being true**: `create()` and `updateStatus()` both invalidate, or a slug probed before provisioning would 404 the customer we just onboarded.
- ❗ **TIME-BASED LICENCE EXPIRY IS MISSING.** We have `status: "expired"` but nothing ever SETS it from time passing — a hospital that stops paying is served indefinitely until a human suspends them. The School ERP denormalises `expiresAt`/`graceUntil` onto the cached registry row and does an in-process date compare: it flips at the exact second with **zero extra DB calls**, because the value is already in the cached entry. **Operator-suspend and licence-expiry are two INDEPENDENT gates — do not conflate them.** This is a revenue hole, not a security one.
- ❗ **NEVER FALL BACK TO PLATFORM CREDENTIALS FOR A TENANT-SCOPED INTEGRATION.** Per-tenant secrets (payment keys, SMTP, gateway creds) live in the TENANT DB — never in a shared `.env` default. An unconfigured tenant that silently uses the platform owner's keys is a billing and liability disaster the day it is a payment gateway. **We already have this smell:** A6's SMTP is global env, so every hospital's mail goes out through the platform's mail server. Acceptable while we are the sender; it must become per-tenant before F-group billing or any white-label deployment.
- **Per-tenant file paths** (`uploads/<slug>/…`) — for A7 Files, so uploads are as isolated as rows.
- **Custom domains: attach → DNS-verify → gate TLS issuance to KNOWN hosts only.** On-demand certificate minting for any host that resolves is a DoS vector (an attacker points DNS at us and makes us mint certs). For A8 white-label.

**Rejected: `lvh.me` for local dev.** We use `<slug>.localhost`, which is reserved by RFC 6761 and resolves to loopback **with no network at all**. `lvh.me` is a public domain owned by a third party: it needs working DNS, it puts tenant slugs into someone else's query logs, and if that registration ever lapses every developer machine breaks at once. Same ergonomics, no external dependency. We also have **no `X-Tenant-Slug` header escape hatch** — the Host is the only selector, in dev and in prod, which is one fewer thing to accidentally trust.

### Two bugs that Orders found, both of which had been sitting in the codebase (2026-07-14)

- **`notify()` reports failure; it does not throw it.** The first version of the critical-result alert wrapped the call in a bare `try/catch` and logged `"CRITICAL result — alert raised synchronously"` on the happy path. But a missing template comes back as an **outcome**, not an exception — so a critical potassium that reached nobody was recorded in the log as **successfully alerted**. A silent failure you know about is an incident; a silent failure that files a success report is a post-mortem in which nobody can work out why the doctor says they were never told. **Check the return value of anything whose job is to reach a human.**
- **There were two provisioning paths and one had forgotten a step.** The CLI script seeded notification templates; `createHospital` — the superadmin HTTP route — did not. Every hospital created through the API therefore had **no** welcome mail, no confirmation, no reminder, and no critical alert; each failed with "no such template", logged and otherwise silent. Nobody had noticed because nothing had yet tried to SEND anything from a hospital provisioned over HTTP. The function's own header warns about exactly this failure mode ("provision now, seed later, and the second step is forgotten") — and it had happened to that very function. **A provisioning path is only correct if it is the only one.** `migrate` re-seeds, so the ten existing hospitals healed on the next run.
- **The test command was lying.** `pnpm test` was supposed to exclude the integration suites; its globs were unquoted, so the shell mangled them and it ran them anyway — and `test:int` then ran them a **second** time. CI was running the integration suites twice, in parallel, against one shared Mailhog. It only surfaced when Orders became the second suite to send mail, and the two started deleting each other's messages. **Integration suites share one Mongo, one Redis and one SMTP; they are isolated in the first two by naming, and mail has no such handle — so `test:int` now runs `--no-file-parallelism`.**

### Four bugs that only a real browser found (2026-07-16)

Typecheck, lint, boundaries and 428 integration tests were ALL GREEN while the product was unusable. Every one of these was found in the first ten minutes of driving the actual screens with Playwright, as the actual roles.

- **The login refused valid credentials.** `device: z.string().max(120)` — and the web client sends `navigator.userAgent`, which is ~117 characters in desktop Chrome. UNDER the cap by a hair, and over it in headless Chrome and plenty of real browsers. So login worked _by luck_, on some machines. The trap sat three lines below a comment that said "No max-length trap ... on login". **Nobody may be locked out of their hospital because their browser is chatty**: cosmetic fields are truncated, never a reason to refuse.
- **The RECEPTIONIST could not register a walk-in.** The doctor dropdown was populated from `listStaff` (`user:read`), which that role does not hold — 403, empty dropdown, button permanently disabled. The EXISTING appointments screen had the identical bug and had shipped with it: broken for the one person who uses it most. Nobody noticed because nobody had logged in AS a receptionist.
- **The doctor's order pad was empty.** Built from `/services`, which needs `billing:read`, which DOCTOR deliberately lacks. My own permission decision broke my own screen — and the fix was a better distinction, not a wider grant (the rate card is not the bill).
- **`limit: 200` was a 400.** The server caps at 100. `.catch(() => undefined)` swallowed it and the screen rendered "no patients" — a lie that looks like an empty hospital. **A silent catch turns a bug into a mystery**; surface it or do not catch it.

The pattern: **every one of these was a permission or contract mismatch between a screen and the API, and no amount of server-side testing can see them.** Drive the UI, as the role, before believing it works.

### Row scope is PER-REQUEST, not per-collection (2026-07-16)

**`prescription:create` was `own`-scoped, and no doctor could have written a prescription.**

`authorize` publishes ONE scope into the request context, taken from the route's permission (`level: permission.scope ?? "tenant"`), and EVERY repository read in that request obeys it. So under `own`, composing a prescription looked up the encounter with `{ createdBy: <the doctor> }` — and the encounter was created by RECEPTION. Every doctor in the country would have got "Encounter not found".

This is the third instance of the same family (`RECEPTIONIST` had no `user:read`; the doctor's order pad needed `billing:read`): **a permission decision that protects the object breaks the workflow around it.** The tell is always the same — the scope or grant is described in terms of the object, and the bug is in the OTHER collections the request happens to touch.

Rules:

- Before giving a permission `own` scope, ask what ELSE its routes read. `own` is safe only when the request touches one collection whose `ownField` is meaningful.
- `order:create` has always been `branch`. A prescription is the same kind of act — a clinical decision taken inside a branch — and own-ness is not what protects it. A doctor covering a colleague's list MUST see the drugs their patient is on, and `own` hides exactly that from exactly them.
- **When a scope forces you to write an unscoped-read bypass, the scope is wrong.** The bypass was deleted when the scope was fixed, and the result is strictly safer: a branch-restricted pharmacist now cannot dispense another branch's prescriptions, where the bypass would have handed them the whole hospital.

### A test that cannot fail is not evidence (2026-07-16)

All 20 prescription tests passed. Then the double-charge bug was deliberately re-enabled — billing charging every pharmacy order at placement — and **all 20 still passed**.

The helper signed the prescription and delivered `prescription.signed`, but never delivered the `order.placed` its consumer raises. So "signing a prescription does not charge the patient" passed because the event that would wrongly charge **was never put in front of the consumer that must ignore it**. The test asserted nothing and looked identical to one that asserted everything.

Falsification found this; nothing else could have. Green means nothing until you have watched the test go red for the reason it exists. **Deliver the whole event chain in integration tests, not just the first hop.**

### An entitlement-gated route makes an RBAC "may NOT" probe pass for the wrong reason (2026-07-16)

The RBAC matrix ran on `PLAN_CLINIC`. It was fine only so long as every route's feature happened to be in `CLINIC_FLAGS` — the pharmacy routes gate on `module.pharmacy.dispensing`, which a clinic correctly does not buy.

The half that failed loudly was harmless ("denied but holds `pharmacy:dispense`"). **The dangerous half is silent:** a "may NOT" probe against an unentitled route PASSES, because `authorize` checks entitlement FIRST and both layers answer 403. The role could have held the permission all along and the matrix would still have called it denied.

The matrix tenant is now on `PLAN_ENTERPRISE`: on the fullest plan a 403 is always a permission decision, which is the only thing that makes the suite mean what it says. **PHARMACIST was also added to `ROLES_UNDER_TEST`** — the only role that may hand a human being a controlled drug had never had a single route probed.

### `$lines.0.field` is not array indexing in an aggregation `$expr` (2026-07-16)

The over-dispense guard — the thing standing between a patient and 12 tablets of a drug they were prescribed 10 of — never ran. In an aggregation expression a dotted path across an array does not subscript it: `$lines.dispensedQty` evaluates to an ARRAY of every line's value, and the `0` in `$lines.0.dispensedQty` is read as a field name. `$add` got an array and the update died with a type error.

It failed CLOSED, so nothing was over-dispensed — luck, not design. Use `$arrayElemAt`. And note what made this findable: a test that dispenses one tablet too many and expects to be refused. **Every database-enforced invariant needs a test that actually violates it.**

### A permission nobody holds is a feature nobody has (2026-07-16)

`admission:create` and `admission:discharge` had been in the catalog since Phase 1C and were granted to **no role at all** — not the doctor, not the nurse, not reception. Every admit route would have answered 403 to every human in the building.

That is the THIRD instance of one family, and it is worth naming because it will happen again:

| Bug                                                     | Shape                                                    |
| ------------------------------------------------------- | -------------------------------------------------------- |
| `RECEPTIONIST` had no `user:read` → doctor dropdown 403 | the permission existed; the role that needs it lacked it |
| `prescription:create` was `own`-scoped → encounter 404  | the grant was right; the SCOPE broke the workflow        |
| `admission:create` held by nobody → every admit 403     | the permission existed; nobody at all had it             |

The catalog is written top-down from a document (Doc 02), and the grants are written per-role. **Nothing checks that every permission has at least one holder**, so a permission can sit in the catalog for months looking like a feature. Two cheap defences, neither built yet:

1. A test that fails when a permission is held by no `DEFAULT_ROLE` — a deliberate allow-list for the genuinely superadmin-only ones.
2. When adding a route, log in AS the role that will use it. Every one of these three survived typecheck, lint and a full green suite.

### The permission gate must decide the REQUEST, not just the rendering (2026-07-16)

The ward screen wrapped the "this stay owes" figure in `<PermissionGate permission="billing:read">` and then fetched the bill unconditionally. DOCTOR does not hold `billing:read` (deliberately — a patient's means must not shape their treatment), so **every doctor opening a ward chart got a 403**, swallowed by a `.catch` and invisible on screen.

It was not invisible in the audit trail. Denials are recorded ON PURPOSE, because "forty denials from one account in a minute is somebody mapping the permission surface" (`middleware/authorize.ts`). A screen that manufactures a denial every time a doctor opens a chart buries that signal in noise we generated ourselves — which is how a real intrusion goes unnoticed.

**A hidden component whose data still gets fetched is not gated; it is decorated.** Gate the call.

### A rejected auth cookie is worse than no cookie (2026-07-16)

A user pasted a screenshot of a permanently blank `/dashboard` — no data, no login form, a `401` from `/auth/refresh` in the console — and reported they could not reach the login page, even after restarting the infrastructure.

The `hms_refresh` cookie is `httpOnly` (correctly — JavaScript must never read it), so **nothing on the client can delete it.** The Next.js route guard treats its mere PRESENCE as "signed in". So a cookie the server had already rejected sent the browser in a circle: `/dashboard` renders → its refresh 401s → the app redirects to `/login` → the guard sees the cookie and redirects to `/dashboard`, where it stops on a blank page. Reproduced in a real browser: final URL `/dashboard`, empty body, exactly the user's screenshot. It is NOT a spinning loop — it settles on the blank page, which is why it looks like "the app is broken" rather than "I am stuck in a redirect".

Restarting the server cannot help: **the broken state is in the user's cookie jar, and the server is the only party that can remove it.** Fix, in three layers: (1) the API now clears the cookie on any 401 from `/auth/refresh` — root cause; (2) the route guard has an escape hatch (`?reason=` on `/login` is not redirected away); (3) `Protected` sends `?reason=expired` so the guard and the client agree the session is dead. Only on 401 — a 500 from a Mongo blip means "ask again", and clearing then would log out the whole hospital on a hiccup.

**Lesson: an httpOnly cookie the server has invalidated must be actively cleared BY the server, because no one else can. "Presence = authenticated" and "the client can recover on its own" cannot both be true.**

### A safety mechanism absent from the database looks exactly like a safety mechanism that is broken (2026-08-14)

The first server-side safety probe against the local `sunrise` tenant reported seven catastrophic results: **two nurses both succeeded on the same dose**, second attempts created duplicates, and every idempotency replay wrote a new row. Every one of them is the headline property M3 was built to guarantee, and all seven were reported by a probe that was working perfectly.

The product was not wrong. **The database was two migrations behind.** `hms_sunrise` had 47 migrations and no `one_administration_per_dose_slot` index — 0048 and 0049 had never been applied. They had never been applied to **any** of the four local tenants, because migrations run inside `provisionTenant` and `seed:demo` skips provisioning for a hospital that already exists. Nothing else converges a tenant, and nothing warns. After `pnpm seed:migrate --all`, all seven passed.

Two things follow, and the second is the important one.

First: **the risk register predicted this in July and scored it 12** (T2, "mixed schema versions"), with the mitigation "per-tenant migration tracking + convergence metric". The tracking exists. The _metric_ — the thing that answers "is every tenant current?" without being asked — was never built, and its absence is exactly what let this sit unnoticed on a developer machine for weeks.

Second: **a uniqueness constraint is invisible until it is contradicted.** Nothing in the app, the gate, the OpenAPI or the test suite reads differently on a database missing an index — the integration suite passes because it builds its own database, correctly migrated, every run. The only way to see it was to try to violate the rule and watch nothing stop you.

**Lesson: verify the schema, not just the data, before trusting any result taken against a long-lived database.** A validation environment that checks its own contents and not its own schema will certify a database that cannot enforce the thing being validated. The `--verify` in `seed:validation` checked 19 facts about the data and would have passed happily on an unindexed database; that was a real gap in it. And when a safety probe reports that a safety mechanism has failed, **the first hypothesis is that the mechanism is not installed** — a human meeting this on a handset would have raised duplicate administration as a P0 and been wrong.

## 7. Lessons Learned

- (2026-08-13, M3-S6) **A route and its client can each be correct and be wrong together, and nothing in a normal gate can see it.** `POST …/vitals` and `POST …/medication-administrations` both carried `idempotent()` from the day they shipped, and the client methods for both took no key — so the middleware could never fire for any caller. The route was right, the client was right, the OpenAPI documented the header, typecheck was silent, and the integration tests passed because a request with no key is honoured by design. Found by hand in M3-S4 and again in M3-S5A, one slice apart, each time only because somebody happened to be reading that route. S6 turned it into a gate check (`checkClientContract.ts` §6: every operation declaring `Idempotency-Key` must have a client that sends one) and it immediately found **eleven more** — patient registration, encounter creation, admission, prescription creation, stock receipt and adjustment, insurance claims, death records, appointments and reschedules. Lesson: **when two halves must agree and neither is wrong alone, the agreement itself needs a test.** The same shape as `Matches<contract, type>` and the RBAC route inventory — and the reason to reach for it is that a hand-audit found the same bug twice.
- (2026-08-13, M3-S6) **A hand-maintained list of "everything that must satisfy X" will be missing the newest thing.** The branch-key invariant was extended in M3-S5A after falsification found it stopped at M2, and by M3-S5B the medication round's key was already absent again — one slice later, the same gap, for the same reason. It now walks `queryKeys` itself and fails when a key is not explicitly classified as branch-scoped or hospital-wide. Lesson: **enumerate the source, not your memory of it** — if the check can derive its own subject list, it cannot go stale, and the classification becomes a thing you must state rather than a thing you must remember.

- (2026-07-12) Writing editions _after_ modules exposed missing modules (dialysis, physio, ED triage…). Lesson: **map packaging → capabilities early**; the sales lens finds architecture gaps that the engineering lens misses.
- (2026-07-12) A mid-review architecture pivot (shared-collections → DB-per-tenant) touched 7 documents. Lesson: keep tenancy assumptions centralized (Doc 03 §1 + ADR) and referenced, not restated, elsewhere — restatements are what go stale.
- (2026-07-12) ADR-0003 (Vite SPA) was correct for its stated scope and superseded within a day when the scope statement changed (public/SEO/white-label surfaces became first-class). Lesson: **an ADR is only as durable as its Context section** — write the scope assumptions explicitly so it's obvious when they break; the supersession process worked exactly as designed.
- (2026-07-12, Phase 1B) The module boundary rule _forced_ a better design. Putting `users`, `credentials` and `roles` in one "auth" module was the obvious move, and it would have created an import cycle (auth needs roles for the token; rbac needs users for bindings). Splitting identity into `users` ← `auth` / `rbac` removed the cycle **and** produced a module where every secret in the platform lives in exactly one folder. Lesson: **when a boundary rule is inconvenient, the design is usually wrong, not the rule.**
- (2026-07-12, Phase 1B) The auth suite passed on its first run — which was itself suspicious. Deliberately breaking the tenant-claim check (`if (false && …)`) proved the isolation test failed as intended; without that step, a vacuous pass and a real pass are indistinguishable. Lesson: **for the assertions that matter most, verify the test fails when the property is removed.** A green suite only means something if you know it can go red.

- (2026-07-14, A2) A route comment asserted "`plan:manage` is granted to no hospital role" — and it was false. TENANT_ADMIN held it, and the demo hospital upgraded itself to Enterprise. The comment survived my own code review because I read it as documentation instead of testing it as a claim. Lesson: **a comment asserting a security property is a hypothesis, not a fact.** Every claim of the form "X cannot do Y" must have a test that tries Y as X.
- (2026-07-14, A5) The audit hash chain reported TAMPERING on a trail nobody had touched — Mongoose silently defaults an array path to `[]`, so entries were hashed one way and stored another. It compiled, it passed typecheck, and it was completely wrong. Lesson: **hash what you have actually round-tripped through the database, never the object you intended to store** — and for a security control, the false-positive path is as dangerous as the false-negative one, because the first false alarm teaches everyone to ignore the alarm.
- (2026-07-14, A5) The same bug also proves the value of testing the _detector_: I only found it because I sealed a real chain and then falsified a real row in MongoDB to watch the alarm fire. Lesson: **a tamper-detection system you have never seen catch a tamper is a decoration.**

- (2026-07-14) **`z.coerce.boolean()` on an environment variable reads `"false"` as `true`.** Env vars are strings and every non-empty string is truthy, so `PASSWORD_REQUIRE_COMPLEXITY=false` silently enabled complexity. Use the `envBool()` helper in `config/env.ts`, which parses the spellings people write and REJECTS anything else. A security flag that reports itself ON while being OFF is the worst possible failure mode.
- (2026-07-14) **`<slug>.localhost` resolves to `::1` (IPv6) BEFORE `127.0.0.1`.** Binding the API to `0.0.0.0` is IPv4-only, so the browser could not reach an API that `curl` reported as perfectly healthy — curl silently falls back to IPv4, a browser does not. In dev, bind dual-stack (leave `API_BIND` empty). Lesson: **when the browser fails but curl succeeds, suspect the address family before you suspect the code.**
- (2026-07-14) **A default is a decision.** `TENANT_BASE_DOMAIN` defaulted to the real production domain, so an unconfigured process was configured _for production_ — and since `*.paperlesstech.in` has wildcard DNS to the live server, our own setup docs pointed a developer's browser at it. Defaults must fail SAFE, and for an environment-shaped setting "safe" means "local". Production names its own domain explicitly.

- (2026-07-14, A6) **The two ways a job can be "not finished yet" look identical, and treating them alike sends the message twice.** The notification ledger claimed a row, then sent. On redelivery the obvious rule is "re-send unless it is already `sent`" — reasoning that a `pending` row was abandoned by a sender that CRASHED, and that skipping would lose the message forever. That reasoning is correct about the dead sender and blind to the other case: `pending` equally describes a sender that is alive and _inside the SMTP call right now_. The recovery path for a corpse fired for a healthy handler, and two racing deliveries put two emails in the inbox. The fix is a **lease** (`claimedAt`): a fresh lease means "someone is doing this" and a stale one means "someone died doing this" — the same mechanism the outbox relay already used to reclaim its own crashed rows, which is a hint the pattern should have been reached for immediately. Lesson: **whenever a retry can overlap the thing it is retrying, "in progress" and "abandoned" must be distinguishable in the data, not inferred from a status.**
- (2026-07-14, A6) **Two BullMQ Workers on one queue SPLIT the jobs; they do not each receive them.** Consuming the `events` queue from the API (alongside `apps/workers`) would have meant roughly half of all bookings never produced a confirmation — and the half that did would have looked like proof the feature worked. A per-concern queue with an explicit fan-out (`queuesFor()`) is not ceremony; it is the difference between a working feature and one that is 50% broken in a way no demo reveals.
- (2026-07-14, A6) **A delayed job should carry an ID, not a decision.** The appointment reminder re-reads the appointment when it fires rather than trusting what was true at booking time — so cancelling or rescheduling needs no job-cancellation logic anywhere, and a patient can never be reminded to attend an appointment that is not happening. The alternative (cancel/reschedule the Redis job on every state change) puts the truth in two places and makes correctness depend on a durable database and a volatile queue agreeing. They will not agree. **The queue is a trigger; the database is the truth.**
- (2026-07-14, A6) A suite that asserts on a MOCKED transport proves only that we called the library. The notifications suite talks to a real mail server (Mailhog, in dev and in CI) and asserts on what actually arrived in the inbox — which is what caught the double-send. Lesson: **assert on the outcome the user experiences, not on the call you made.**

## 8. Common Mistakes to Avoid (grows with experience)

- Using `suppliers`/`equipment` as collection names (rulings N1/N2 — they're aliases/views of `vendors`/`assets`).
- Putting business logic, DB access, or business API routes inside Next.js (`app/api/*`) — Next.js is presentation-only; Express is the only API (ADR-0012, ruling N9).
- Scaffolding new frontend features with Vite — Vite survives only as Vitest + `packages/ui` playground tooling.
- Putting per-hospital data in the master DB or vice versa — check Doc 03 §2 placement table every time.
- **Granting a commercial permission to a hospital role.** `plan:manage` / `featureflag:manage` decide what a customer PAYS FOR. They belong to the SUPERADMIN group and must never be inherited by TENANT_ADMIN — a customer who can toggle their own flags has a free upgrade. (Happened once; see §1.)
- **Browsing a tenant on the real domain in local dev.** `*.paperlesstech.in` has **wildcard DNS pointing at the production server** — `demo.paperlesstech.in:3000` in a browser goes to production, not your laptop. Use `<slug>.localhost` locally (`TENANT_BASE_DOMAIN=localhost`); it resolves to 127.0.0.1 with no hosts-file entry.
- **Hardcoding an API base URL in the frontend.** `http://localhost:4000` resolves to NO hospital: the browser cannot set `Host`, so the hostname it is browsing is the only thing that selects a tenant database. Configure a PORT (`NEXT_PUBLIC_API_PORT`) and derive the origin from `window.location.hostname`.
- **Shipping a migration without running the fleet job.** A tenant provisioned before the migration keeps running the old schema forever and fails in ways that look like bugs (an admin with zero permissions). Run `pnpm --filter @medicore/api migrate -- --all` after any release that adds a migration or changes the permission catalog.
- **Assuming a loopback address means a local database.** (2026-07-13 near-miss.) An SSH tunnel — `ssh -L 27018:127.0.0.1:27017 user@remote` — bound the _same_ loopback port as our dev Mongo and silently won the bind over Docker. Every connection to `127.0.0.1:27018` then reached a **remote** server, and our integration tests call `dropDatabase()`. Nothing was lost, but only by luck. The harness now refuses to run unless the host is loopback **and** the server has no auth (our dev container runs open; real servers do not), and it will only drop databases named `test_*` / `hms_test-*`. If a suite suddenly refuses to run, check `lsof -nP -iTCP:27018 -sTCP:LISTEN` and `docker ps` — something else has the port.
- **Letting a containerized replica set advertise an address that is only true inside the container.** (2026-07-14, found while writing Compass instructions.) A replica-set client does not talk to the server you named — it asks that server who the members are, **discards your address**, and reconnects to the one it is given. Our mongod listened on 27017 internally, so it advertised `localhost:27017`; on the dev Mac that address is an unrelated **`school_mongodb`** from another project. Docker isolation was never breached — both containers publish a port to the host on purpose, and the _client_ walked from one to the other. And because a replica set is named `rs0` by default on both sides, the driver could not tell it had crossed projects: it believed it had simply found its primary. The only thing that stopped a cross-project connection was luck — the other server advertised a Docker-internal hostname that did not resolve (`getaddrinfo ENOTFOUND mongodb`). **Fix: mongod now listens on 27018 _inside_ the container too, published `27018:27018`, advertising `localhost:27018` — one address that is true on both sides.** Discovery is self-consistent, so a client that forgets `directConnection=true` still lands on the right server. Keep the flag regardless: from inside another container, `localhost` means that container. Same class of bug as Kafka's `advertised.listeners`. **Never "normalize" the internal port back to 27017.**
- **Assuming a `services:` container in GitHub Actions can be a replica set.** It cannot — Actions gives no way to pass a command, so `mongo:7` there is a **standalone**, and a standalone supports no transactions at all. Ours was standalone while the comment above it claimed otherwise, which would have failed at the first `withTransaction` in P2 with an error pointing nowhere near the cause. CI now starts Mongo with an explicit `docker run --replSet`, waits for the primary, and **proves a transaction commits before any suite runs** — so the infrastructure fails loudly at its own step rather than inside an unrelated assertion.
- **Trusting a new test suite that has only ever passed.** A suite's first green run tells you nothing — it is equally consistent with "the code is correct" and "the suite asserts nothing". The RBAC matrix suite was only believed after it was **falsified**: `authorize()` was deleted from a route (it named the route) and the P2 branch-scope bug was reintroduced (it reproduced the exact symptom). Two near-misses on vacuity were caught this way and are now guarded in the suite itself: `routeInventory` returning `[]` after an Express upgrade would make every route test pass, and a `permissionsOf()` that silently resolved to an empty set would make every "expect 403" pass. **Break the code on purpose and watch the test go red, or you have not tested anything.**
- **Letting an EMPTY value carry meaning.** (2026-07-14, the P2 branch-scope bug — the best lesson of the phase.) `userRoles.branchIds: []` was read as **"all branches"** by RBAC (`rbac.model`: "empty means all branches"; `rbac.service`: "Empty = not restricted") and as **"no branches, fail closed"** by the row filter (`authorize`: `$in: []`). Two halves of one system had held opposite readings of the same empty array **for three phases**, and nothing caught it because every resource was tenant-scoped — the `branch` branch of `scopeFilter` had never executed. The instant `patients` shipped as the first `branch`-scoped collection, **the patient list came back empty for every user in every hospital, including the administrator who had just registered the patient.** Both readings were defensible, which is exactly why `[]` must not be the thing that decides. Fix: the binding now STATES its intent (`branchScope: "all" | "branches"`), and fail-closed is kept precisely where it belongs — a binding that says it is confined and names no branch still gets nothing, so a list cleared by a future bug can never silently become "the whole hospital". **Generalize this: when a value's emptiness is load-bearing, store the intent, not the absence.**
- **Shipping a shape change through a cache that outlives the deploy.** Adding `allBranches` to the `perm:{userId}` bundle would have been read as `false` on every entry already in Redis — i.e. "confined to no branches" — so every user would have seen an empty patient list for up to a full TTL after release and then silently recovered. A bug that heals itself in fifteen minutes is one nobody can reproduce and everybody remembers. Fix: the key is **versioned** (`perm:v2:{userId}`). **Bump it whenever the cached shape changes** — a cache is not a source of truth, so abandoning it is cheaper and safer than migrating it.
- **Stamping fields in Mongoose `pre("save")`.** Schema validation runs _before_ save hooks, so a `required` field stamped there fails validation. Stamp in `pre("validate")` (this is why `tenantScopePlugin` does).
- **Writing an integration test that touches Mongo but not Redis.** The tenant registry is a **read-through cache**: dropping the master DB while `tenant:{slug}` is still cached leaves the app resolving a tenant that no longer exists (symptom: "Slug already taken" on a freshly dropped database). Test setup must drop **both** — `dropDatabases()` **and** `flushTestCache()`. The application never produces that split-brain state on its own; only a test harness can.
- **Asserting on a fail-soft dependency without running it.** Cache helpers fail soft by design, so an auth test that checks "the logged-out token is blocklisted" **passes vacuously with no Redis running** — "revoked" and "never revoked" look identical. This is why the auth suite asserts Redis is reachable and CI runs a real `redis` service. Any future assertion that rests on a fail-soft path needs the same treatment.
- **Importing an ambient `const enum` from a library under `isolatedModules`** (e.g. `Algorithm.Argon2id` from `@node-rs/argon2`) — it typechecks in an editor and fails the build. Pin the value and assert the result instead (`core/crypto/password.ts`).
- **Forgetting `asyncHandler` on an async Express route.** Express 4 does not forward rejections from async handlers: the error never reaches the error middleware and the client hangs until timeout. Every async route wraps in `asyncHandler` (`core/http/asyncHandler.ts`).
- Aggregating dashboards from OLTP collections "temporarily."
- Confusing the hospital's own helpdesk (`helpdeskTickets`, tenant DB) with SaaS support (`supportTickets`, master DB).
- Treating `00-PROGRESS-TRACKER.md`/this file as optional paperwork — they are the only memory the next agent has.
